Finding ids

Everything audit_website, recheck_website and the PDF audit can report, by id. Use this page to decide what a CI job fails on, to tell an agent which findings are its job and which are the hosting provider's, and to look up what a fixed / new line in a re-check actually means.

How ids work

  • Shape. area.rule, optionally followed by @target: sec.header.hsts is site-wide, seo.h1.missing@/pricing/ is about one page, links.broken@https://…/file.zip about one link, a11y.color-contrast@/#dark about one axe rule on one page in one colour scheme. The part before @ is listed below; the target is whatever the finding is about.
  • Stable. The same problem produces the same id in every run, which is what makes the re-check diff (fixed / open / new / unverified) and the weekly Monitor comparison possible. Titles and details are human text and may change; ids do not.
  • Severity is one of high, medium, low, info. Some rules have a fixed severity, others pick it from a threshold (listed below). info is context, never a defect.
  • Areas: sec security · perf performance · seo technical SEO · a11y accessibility · ux usability · journey customer journeys in a real mobile browser · links broken links.
  • Unverified in a re-check means the target could not be checked this time (link blocked or timed out, page returned an error), so it is reported neither as fixed nor as new.
  • Accessibility ids (a11y.*) come from axe-core on the page itself: nodes inside third-party iframes (video players, maps) are left out, and colour-contrast results are dropped for elements that are still faded by a scroll-linked animation or that measure below 1.3:1 (a background the test cannot see, not readable text).
  • Broken links are reported only with the page they were found on; DNS failures are re-checked before they count.
  • Blocked sites. When the site refuses us – the home page answers 4xx, at least 30% of crawled pages return 403/429/503 or drop the connection, or the browser cannot open any key page – the audit fails with the error BLOCKED instead of producing findings measured on an error page. Allow the Webskan user agent (see /bot/) and run it again.
  • Performance ids (perf.*) move with network conditions. Gate on them with a threshold you accept, not on their mere presence; the Monitor's weekly diff excludes them for the same reason.

sec.wp.insecurehighThe detected WordPress core version is marked insecure by the WordPress.org version catalogue (later releases patch known vulnerabilities).Update core at least to the last maintenance release of its branch; enable automatic minor updates.

If the admin panel already shows a newer version, the public version string is stale – ignore.
sec.vuln@js:<library>lowA JavaScript library loaded by the page (version read from the file URL) matches a retire.js vulnerability entry.Update the theme or plugin that bundles the library, or load a patched version.
sec.wp.plugin.closed@<slug>mediumA detected plugin has been closed in the WordPress.org directory, so it no longer receives updates.Replace it with a maintained alternative.
sec.wp.plugins.outdatedlowOne or more detected plugins have a newer version in the WordPress.org directory and no known vulnerability for the installed version (those are reported as sec.vuln@… instead).Update plugins; enable auto-updates for the ones you trust.
sec.wp.user-enumlow/wp-json/wp/v2/users returns a JSON list of accounts with slugs to a logged-out request.Restrict the endpoint for anonymous requests (security plugin or the rest_endpoints filter).
sec.wp.xmlrpclow/xmlrpc.php answers with the standard “accepts POST requests only” response.Disable XML-RPC unless the mobile app or Jetpack needs it.
sec.dir-listing@/dir/mediumA directory the page itself loads files from (up to 4 are tried, plus /wp-content/uploads/) returns an “Index of” listing.Options -Indexes (Apache) or autoindex off (nginx).
sec.django.debughighA Django application answers a non-existent address with the technical DEBUG error page.DEBUG = False and ALLOWED_HOSTS in production settings.
sec.django.adminlow/admin/ leads to the Django admin login form (one GET, one redirect; nothing is submitted).Restrict access by IP or VPN, add two-step login and attempt limiting; optionally a non-default URL.
sec.db-panellow/phpmyadmin/ or /pma/ returns a phpMyAdmin login form.Restrict by IP or disable the panel on the public host name; often a host-wide default.
sec.cookie.flags@namelowA session-like cookie set on the home page lacks Secure (on https) or HttpOnly. CSRF tokens are skipped.Set both flags in the session configuration.
sec.mixed-content@/pagehighAn https page loads scripts, styles, images or frames over http://.Use protocol-relative or https URLs; in a CMS, search-and-replace the old http origin in content and theme settings.
sec.form.insecure-action@/pagehighA form's action points to an http:// URL.Change the action to https (or a relative path).

Security score. Reports and scan results carry securityScore (0–100) computed from the sec.* findings: start at 100, subtract 25 per high, 8 per medium and 2 per low finding; missing security headers cost at most 12 points in total; any high finding caps the score at 49. Vulnerability data comes from CVE records (cve.org, © The MITRE Corporation), CISA KEV, retire.js, WordPress.org and WPVulnerability – details on the security score page. For application dependencies (Python, Node.js) there is a separate check: project dependencies, also available as JSON at POST /api/deps/check?format=json.

Performance – perf.*

Measured with Lighthouse on an emulated mid-range phone over simulated 4G, from the audit location. Values vary between runs; gate with a margin.

IdSeverityFires whenUsual fix
perf.lighthouse.incompleteinfoThe page did not finish loading within 45 s. No other perf.* finding is produced from that run, because its metrics would be inflated.Find the resource that never resolves from outside your network (third-party script, blocked geo); check the page in PageSpeed Insights.
perf.score.mobilehigh < 50, medium 50–89Lighthouse mobile performance score below 90.Work the specific perf.* findings below; the score follows.
perf.lcp.mobilehigh > 4 s, medium > 2.5 sLargest Contentful Paint above the Google threshold.Preload the hero image or font, serve it in a modern format and the right size, cut render-blocking CSS/JS, fix slow TTFB.
perf.cls.mobilehigh > 0.25, medium > 0.1Cumulative Layout Shift above threshold.Width/height on images and embeds, reserve space for banners and ads, font-display: optional or matching fallback fonts.
perf.tbt.mobilehigh > 600 ms, medium > 300 msTotal Blocking Time above threshold (the lab proxy for INP).Defer or remove heavy scripts, split long tasks, load tag managers and chat widgets after interaction.
perf.weight.mobilemediumTotal transferred bytes above 3 MB.Compress and resize images, drop unused scripts and fonts.
perf.heavy-script@file.jsinfoTBT is above 300 ms; names the single script with the most main-thread time.Profile that file; it is usually the first thing to defer or remove.
perf.blocking-scriptsmedium ≥ 3 scripts, else lowSynchronous JavaScript files in <head> without defer/async. Scripts at the end of <body>, scripts with a non-JavaScript type (taken over by an optimiser such as Rocket Loader) and cookie-consent scripts are not counted.Add defer, or move the script to the end of <body>.
perf.opp.<lighthouse-audit>medium ≥ 1.5 s saving, else lowA Lighthouse opportunity estimates ≥ 0.5 s or ≥ 50 KB of savings (e.g. perf.opp.render-blocking-resources, perf.opp.uses-responsive-images).Follow the Lighthouse audit of that name.
perf.images.oversized@/pagelowRaster images have several times more pixels than their rendered size on a phone. SVG files and data: lazy-load placeholders are ignored.srcset/sizes or an image CDN; export at the displayed size.
perf.images.no-dims@/pagelowThree or more images without width/height on a page whose CLS is above 0.1.Add the attributes or aspect-ratio in CSS.
perf.slow-response@/pagemedium > 5 s, low > 2.5 sTime to first byte of the HTML above threshold. A slow page is measured two more times after the crawl, one request at a time; the median of the three counts.Page cache, object cache, fewer plugins, better hosting, a CDN in front.
perf.compression.nonemediumThe HTML response is not gzip/brotli compressed.Enable compression at the server or CDN.

Customer journeys – journey.*

The audit walks the site like a customer on a phone: opens the menu, searches for a word from the page, finds the contact form, adds a product to the cart and reaches checkout (nothing is submitted or paid), and requests a non-existent address. Each finding carries a screenshot.

IdSeverityFires whenUsual fix
journey.nav.failhighTapping the mobile menu button reveals no links.Usually a JavaScript error or a CSS breakpoint mismatch; see ux.js-errors.
journey.nav.not_foundlowNo menu or menu button could be recognised on the first mobile screen (after closing a cookie banner). Unusual buttons can be missed, so treat it as a prompt to look.A visible hamburger button or inline links above the fold.
journey.search.failmediumSite search ends on an error page.Fix the search endpoint; test with a plain word.
journey.search.warnlowSearching for a word taken from the page's own heading returns nothing.Reindex, or check the search ignores accents and word forms.
journey.404.soft404mediumA random address returns 200 at that address.Return a real 404 status with the error page.
journey.404.redirectmediumA random address redirects (301/302) to another page, usually the home page, which answers 200.Remove the catch-all redirect rule or “redirect 404 to homepage” plugin setting; return 404 with an error page.
journey.404.blankhighThe error page is empty.A 404 page with menu, search and a link home.
journey.404.shows_homelowA non-existent address returns 404 but the application shows its start screen with no “not found” message.Add a not-found view with a message and a link home; keep the 404 status.
journey.404.no_way_outmediumThe error page has no navigation.Same as above.
journey.404.other_shapelowThe site's URLs end in .html/.php and a wrong address with that ending gets the site's own 404 page, but a wrong address without it gets a bare server page with no navigation. The main 404 checks use the ending most of the site's links have.Route every 404 to the same error page (error_page 404 in nginx, ErrorDocument 404 in Apache, or the CMS setting).
journey.404.server_errorhighA non-existent address returns 5xx.Fix the router or rewrite rule that crashes on unknown paths.
journey.shop.failhighProduct → cart → checkout does not reach the checkout page; the reason is in the title.Reproduce on a phone with a fresh session.
journey.shop.login_requiredhighCheckout demands an account.Enable guest checkout.
journey.shop.no_payment_methods_visiblemediumThe checkout page shows no payment methods.Show accepted methods before the customer types anything.
journey.shop.many_fieldsmediumCheckout has more than 14 fields.Hide optional fields, enable autofill, drop the account-creation block.
journey.shop.add_button_disabled_(out_of_stock_or_variant)lowThe tested product could not be added (out of stock or variant required).Check the customer gets a clear message; not a defect by itself.

Links – links.*

IdSeverityFires whenUsual fix
links.broken@<url>mediumA link found on the crawled pages (internal or external, up to 500 checked, up to 40 reported) returns 4xx/5xx or no response after a retry. What to gate on

  • Always fail: any high. They are deterministic (redirects, exposed files, mixed content, robots, viewport, broken journeys) or far past a threshold.
  • Fail on new medium findings in a re-check, not on all medium findings – legacy debt should not block today's deploy, regressions should.
  • Do not gate on info, on perf.* without a margin, or on links.broken@ for external hosts you do not control (watch them in the Monitor instead).
  • The CI script and the CLAUDE.md block that implement this are in Make your coding agent verify every deploy.
