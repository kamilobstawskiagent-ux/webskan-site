We reported an exposed file to 17 online shops. A week later, 13 are still serving it

While scanning the home pages of small Polish online shops we kept finding files that should never be public: phpinfo() pages, PHP error logs, a database admin panel. We sent 17 shops one short e-mail each: which file, at which URL, and how to close it. Today we re-checked every URL. Result: 4 closed, 13 still open, 0 replies.

What we did

Between 11 and 13 November 2026 we sent 17 e-mails to the contact address published on each shop's site (typically shop@, contact@ or office@). Each message covered exactly one file and had the same structure: the URL, two sentences on what the file reveals, a two- or three-step fix, and a line saying this is the only message we will send and no reply is needed. Before sending, every file was verified by hand: HTTP 200 and content that is actually what it looks like.

On 17 November – four to six days later – we requested the same URLs again. “Closed” means the URL now answers 403 or 404. “Open” means it still returns the same kind of content; we matched content signatures rather than trusting the status code, for the reasons described in Your deploy just published .env. We are not naming the shops.

Nobody replied to any of the 17 messages – which is fair, since we said no reply was needed.

Seventeen shops is a small sample, so do not read the percentages as a statistic about e-commerce in general. Three patterns were clear enough to be worth writing down.

1. Fixes happen within hours or not at all

All four files disappeared on the day the message was sent, three of them within a few hours. In the days after that, not a single additional file was closed. There is no “we'll get to it next week” group: the message either reaches someone who knows what to do with it straight away, or it is gone.

That matches how a small shop's inbox works. shop@ is read by whoever handles orders and returns. A message about /wp-content/debug.log is neither; it looks foreign, and the person who could act on it – the freelancer who built the site, the hosting company – never sees it.

2. Logs get fixed more often than phpinfo pages

Three of seven logs were closed, but only one of eight info.php files. With numbers this small it may be chance, but there is a plausible explanation: a log with thousands of error lines looks like a problem to anyone who opens it. A tidy table with a PHP version looks like something that is probably supposed to be there.

The tidy table is the more useful one to an attacker. All seven info.php pages that are still open report a PHP branch that reached end of life between 2018 and 2020: four on 7.1, one each on 7.2, 7.0 and 5.6. Some hosts backport security patches to old branches, so this is not automatically a vulnerability – but it is exactly the fact someone uses to decide which site to try first.

Of the logs still open, the largest is close to 790 MB today; two others are 0.8 and 0.5 MB. Each contains full server paths and the names of the plugins throwing errors. The database login panel is still open too.

3. Sixteen of 17 shops publish no address for this kind of report

There is a simple standard for it: /.well-known/security.txt (RFC 9116), where a site states where security reports should go. One shop of the 17 had one – and it is one of the four that closed the file (our message happened to go to its general address, so we cannot say whether that mattered). The other sixteen leave a reporter no route except the orders inbox.

What to take from this if you build or run sites for clients

Ship a security.txt with every site

It is a plain text file. The two required fields are enough:

Contact: mailto:you@your-agency.example
Expires: 2027-11-17T00:00:00.000Z

Point Contact at someone with server access – for a client site that is usually you, not the client. Expires is mandatory and the RFC recommends keeping it under a year out, so put the renewal in the same calendar as the domain and the certificate. Ours: webskan.com/.well-known/security.txt.

Tell the client where technical mail goes

One sentence for whoever reads the shop inbox: anything about the website, server, domain, certificate or “a file at this URL” gets forwarded to [name] the same day. The same rule catches renewal notices from the registrar and the host, which also land in the general inbox and also look foreign.

Remove the files before anyone has to report them

Every file in the table is a leftover from normal work: an info.php uploaded to check the PHP version after a migration, WP_DEBUG_LOG switched on for an afternoon. A check that runs after every deploy catches them while the person who created them is still looking. The signatures and server rules are in the exposed-files post; if a coding agent does your deploys, make it verify every deploy.

If you are the one reporting

What we would keep: one file per message, the exact URL on the recipient's own domain so they can verify it by typing it into a browser, the fix in the message itself, no attachment, no deadline, no follow-up. What we would change: look for security.txt first, and where the site names its developer or agency in the footer, write to them instead of the orders inbox.

Method and caveats

  • The shops come from our November 2026 scans of small Polish online shops' home pages. A message went to every shop with a verified file for which we found a contact address and which we had not written to before.
  • One message per shop, no reminders. We do not know how many were opened; we do not use open tracking.
