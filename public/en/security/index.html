Security score: what we check and how it is calculated

The “Security” score (0–100) shows how many weak points of a site are visible from the outside – the way anyone visiting the site sees them, including bots looking for easy targets. We break nothing and log in nowhere.

Example: what a result looks like

A real audit result for a company website running WordPress, from 21 November 2026 (address withheld). Of its 17 security findings we show three – one of each severity.

Security

13 out of 100. Where the score comes from: 1 important finding (−25), 5 “worth fixing” (−40), 5 minor (−10) and 6 missing headers (−12, the cap). 100 − 25 − 40 − 10 − 12 = 13.

  • importantPlugin “Essential Addons for Elementor” 6.4.0 – 22 known vulnerabilities

    Version 6.4.0 was read from the plugin’s readme.txt. Public vulnerability databases list 22 entries for it; the most serious: account takeover or privilege escalation – an ordinary account can become an administrator (no login needed), CVE-2026-18039, score 8.1/10. 9 of them can be used without logging in and without anyone’s help. The latest version in the WordPress directory (6.8.9) is outside the range of these vulnerabilities – update to it. If your admin panel already shows a newer version, ignore this finding.

  • worth fixingPlugin “Elementor Website Builder” 4.0.2 – 14 known vulnerabilities

    Version 4.0.2 was read from the plugin’s readme.txt. Public vulnerability databases list 14 entries for it; the most serious: cross-site request forgery – a logged-in user (usually an administrator) who clicks a planted link performs an unwanted action, CVE-2026-62062, score 8.8/10. None can be used from outside on its own: 4 need someone to be tricked into clicking a link, the rest need a logged-in account. The latest version in the WordPress directory (4.4.1) is outside the range of these vulnerabilities – update to it.

  • minorWordPress XML-RPC interface is enabled

    /xmlrpc.php responds. It is used for bulk password guessing and amplification attacks; unless you use the WordPress mobile app or Jetpack, disable it.

Note the second item: the vulnerability is rated 8.8/10, yet the finding is of medium severity – none of these vulnerabilities can be used without a logged-in account or without tricking someone into a click. Severity reflects the risk to the site owner, not the number alone.

What we check

  • Known vulnerabilities in the site’s software. We read what the site is built with (WordPress, plugins, theme, libraries) and in which versions, then compare that with a database of published vulnerabilities. The result: “plugin X version Y has a known vulnerability, the fix is in version Z”.
  • Unsupported versions. A WordPress release that WordPress.org marks insecure, PHP past end of life, plugins removed from the directory.
  • Files that should not be visible. Backups, database dumps, configuration files, a code repository, error logs, a database panel.
  • The connection. The certificate and its expiry, the redirect to HTTPS, resources loaded without encryption.
  • Mail spoofing protection. The domain’s SPF and DMARC records – they decide whether someone can send e-mail “from you”.
  • Server and WordPress settings. Security headers, session cookies, a public account list, XML-RPC, directory listing.
  • Django applications. An admin panel open at the default /admin/ address and DEBUG mode left on in production (the error page then exposes the application’s internals).

How the score is calculated

We start from 100 points and subtract for every finding:

Finding weightPointsExample
important−25a plugin with a vulnerability usable without logging in and without anyone else’s action; a publicly reachable database backup; an application left in DEBUG mode
worth fixing−8no DMARC record; a vulnerability that needs a logged-in account or someone tricked into clicking a link
minor−2XML-RPC enabled; an outdated plugin with no known vulnerabilities
  • Missing security headers subtract at most 12 points in total – headers alone do not turn a site red.
  • One “important” finding caps the score at 49. A site with a serious vulnerability does not get an amber score because everything else is fine.
  • Colours: 90–100 green, 50–89 amber, 0–49 red.

The same formula runs in the free scan, the in-depth audit and Monitor, so results can be compared over time.

A new vulnerability? Monitor tells you

Vulnerabilities are published every day, including for versions that were safe yesterday. Webskan Monitor compares the site’s software with the database once a day and e-mails you when a new entry appears: which component, what is at risk, whether it can be used without logging in, and which version to update to. Each vulnerability is reported once.

How we know about vulnerabilities

We maintain our own database of known vulnerabilities in website software – about 40,000 entries today for over 12,000 WordPress plugins and themes and popular libraries – refreshed several times a day from public, official sources (listed below). Every finding carries a CVE number, so it can be checked at the source.

A plugin’s version is read from files the site itself serves. If the site does not reveal a version we say “nothing to compare” – we do not guess.

What the score does not tell you

  • 100 does not mean “cannot be hacked”. We cannot see the admin panel, passwords, server-side code or plugins that leave no trace in the page source.
  • A known vulnerability does not mean “the site is hacked”. It means this version has a documented flaw and is worth updating before someone uses it.
  • The admin panel is authoritative. If Plugins → Installed shows a newer version than our reading, the finding can be ignored.
  • We do not run penetration tests: no login attempts, no form submissions, no checking whether a vulnerability is exploitable. Scanner traffic details: webskan.com/bot.
