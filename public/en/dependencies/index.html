What you get

  • A list of vulnerable packages, most serious first: name, the version in your project and the version that removes every known vulnerability.
  • Every vulnerability with its CVE number and a link to the source, with severity and the fixed version.
  • Packages that could not be checked – those without a pinned version – listed separately instead of silently skipped.

What happens to the file

The file is read in memory and is not stored. Only package names and versions are sent to the vulnerability database – the same information a public registry sees on every install. We do not need or look at your application code.

In a CI pipeline

The same check works from the command line and returns JSON:

curl -s -F file=@requirements.txt "https://webskan.com/api/deps/check?format=json"

The vulnerablePackages field is the number of packages with vulnerabilities; each one carries updateTo, the version to update to.

Continuous monitoring: an e-mail when a new vulnerability appears

Dependencies that are clean today may have a vulnerability announced next month – the code has not changed, the knowledge about it has. A one-off check shows today's state. Monitoring compares the package lists of your projects with the vulnerability database every day and writes only when there is something new.
